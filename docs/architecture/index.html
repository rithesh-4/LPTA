Key point: pass_stack is transient (alive only during MPM.run()), g_events is the accumulated record, and history.json is its serialization. The dashboard only ever sees events.

2 Anatomy of one pass execution

Why a stack, not a “current pass” variable: pipelines nest (Module → Function → Loop). Every BEFORE must pair with exactly one AFTER across nesting.

sequenceDiagram
    autonumber
    participant PM as LLVM PassManager
    participant CB as LPTA callbacks (main.cpp)
    participant ST as pass_stack
    participant EV as g_events

    PM->>CB: BEFORE ModuleToFunctionPassAdaptor (Module)
    CB->>CB: detectIR → metrics snapshot
    CB->>ST: push frame {depth=0}
    CB->>EV: push "before" event

    PM->>CB: BEFORE SimplifyCFGPass (Function entry)
    CB->>ST: push frame {depth=1}
    CB->>EV: push "before" event

    Note over PM: SimplifyCFG mutates the function

    PM->>CB: AFTER SimplifyCFGPass
    CB->>ST: pop topmost frame matching name + ir_ptr
    CB->>CB: delta = before vs after metrics
    CB->>EV: push "after" event (+ IR diff if changed)

    PM->>CB: AFTER ModuleToFunctionPassAdaptor
    CB->>ST: pop outer frame (depth back to 0)
    CB->>EV: push "after" event

    Note over CB,EV: Invariant: MPM.run() returns with an empty stack → "Stack remaining: 0"
The special case: if a loop pass deletes its own loop, LLVM has no valid IR object left to hand back — it fires AfterPassInvalidated instead of AFTER. INVALIDATED events carry metrics-before but no after-state, matched by name alone (topmost, LIFO).
